# Runbook: revisions & scheduled publishing (GDW-035)

How draft revisions and scheduled/instant publishing work, and how to operate
them.

## Revisions

Posts, pages, projects, and links have Payload **versions** enabled
(`versions: { maxPerDoc: 25 }`, no drafts — the custom `status`/`visibility`
workflow is unchanged). Every save snapshots a version.

- **View history:** open a document in the admin → **Versions** tab.
- **Restore:** open a version → **Restore this version**. (Restoring is itself a
  save, so it creates a new version and, if the doc is public, triggers a
  rebuild.)
- Versions live in `_<collection>_v` tables created by the
  `add_content_versions` migration.

## Publishing is event-driven (no polling)

The public site is a **static build** (S3 + CloudFront), so "publish" → "live"
always includes a rebuild (Astro build + S3 sync + CloudFront invalidation),
~1–2 minutes once triggered. There is **no poller**; rebuilds are triggered the
moment content changes.

The CMS Lambda runs in an isolated subnet with **no internet egress**, so it
cannot call GitHub or EventBridge directly. Instead it writes a small JSON
**marker** to the private control bucket
(`georgedallaswebsite-<env>-publish-control`, prefix `publish/`). An S3 event
triggers the **publishing worker** Lambda (`…-publish-worker`), which runs
outside the VPC and has internet access.

```
Manual publish/edit:
  CMS afterChange hook --> S3 "rebuild" marker --> worker --> GitHub workflow_dispatch
    --> rebuild-site.yml (build + s3 sync + invalidate)

Schedule a post for time T:
  CMS afterChange hook --> S3 "schedule" marker --> worker
    --> one-shot EventBridge schedule at(T)  [auto-deletes after firing]
  ...at T:
  EventBridge --> worker --> POST /api/internal/publish-scheduled (HMAC)
    --> CMS flips status=published --> afterChange --> "rebuild" marker --> rebuild
```

Markers and rebuilds are idempotent; rapid edits coalesce because
`rebuild-site.yml` uses `concurrency: cancel-in-progress: true`.

### Scheduling a post

Set **status = Scheduled** and a future **publishedAt**. Scheduled content must
already have its publish metadata (excerpt/SEO title/SEO description for posts)
so the unattended publish cannot fail validation — the admin enforces this on
save. Scheduled and future-dated content is never in the public build
(`publicBuildWhere` requires `status=published` AND `publishedAt <= now`).

To reschedule, change `publishedAt` (the worker overwrites the one-shot
schedule). To cancel, move it out of Scheduled or delete it (the worker deletes
the schedule).

## One-time setup

The rebuild trigger needs a GitHub token. After the stacks deploy:

1. Create a **fine-grained GitHub PAT** with **Actions: read and write** on
   `gdallas/georgedallaswebsite`.
2. Put it in Secrets Manager under `/georgedallaswebsite/<env>/github-token` as
   JSON `{ "placeholder": "<the PAT>" }` (the worker reads the `placeholder`
   key, matching the CDK-generated secret shape).
3. Redeploy the CMS stack so the worker picks up the new value (it is injected
   as an env var at deploy time).

The `webhook-secret` (HMAC between worker and the CMS internal endpoint) is
auto-generated by CDK and shared via env injection — no manual step.

## Migration (Docker only)

Enabling versions requires a generated migration. The Payload CLI is broken on
Windows (tsx mangles `node:` imports), so generate it in Linux Docker per
`docs/runbooks/cms-hosting.md`:

```
# from a built CMS image, with the CI placeholder env vars set
pnpm --filter @georgedallas/cms exec payload migrate:create add_content_versions
```

Commit the generated `*.ts`/`*.json` under `apps/cms/src/migrations/` and add it
to `migrations/index.ts`. Do **not** commit the generated `payload-types.ts`
(gitignored). Committed migrations run automatically on CMS startup
(`prodMigrations`).

## Manual backstop / recovery

If the event-driven path misses something (e.g. the worker was misconfigured),
publish any overdue scheduled content by hand. It is idempotent:

```
CMS_API_URL=https://cms-dev.georgedallas.com \
CMS_EMAIL=you@example.com CMS_PASSWORD=... \
node apps/cms/scripts/scheduled-publish/run.mjs
```

It refuses the production CMS unless `SCHEDULED_PUBLISH_ALLOW_PROD=true`.

## Troubleshooting

- **Published content isn't live:** check the `rebuild-site` workflow run in
  GitHub Actions; check the worker's CloudWatch logs
  (`/aws/lambda/…-publish-worker`) for a dispatch error (usually a missing/expired
  `github-token`).
- **Scheduled post didn't publish at its time:** look for the one-shot schedule
  in EventBridge Scheduler (name `<env>-pub-<collection>-<id>`); check the worker
  logs for the `publish` invoke. Failed publishes are also recorded as a
  `security_event` audit row (action metadata `scheduled_publish_failed`). Run the
  backstop script to recover.
- **Marker not produced:** confirm the CMS has `PUBLISH_CONTROL_BUCKET` set and
  its role can `s3:PutObject` to the control bucket. Markers expire after 1 day.
